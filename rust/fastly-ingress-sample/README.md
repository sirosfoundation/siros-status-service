# fastly-ingress-sample

A sample [Fastly Compute](https://developer.fastly.com/learning/compute/)
service reimplementing `cmd/ingress-router`'s logic (`docs/design.md` §15.6)
on Fastly's edge WASM runtime, using the [`token-format`](../token-format)
crate to verify tokens. This came out of an investigation into whether a
platform-native edge runtime could run this service's JWT-verification +
claim-based routing — see `docs/design.md` §16 for the write-up. **The
decision was to keep `cmd/ingress-router` as the primary, portable
deployment; this sample exists to prove the Fastly path is real, not to
replace it.**

## What this proves

- `token-format` compiles and runs correctly on `wasm32-wasip1` (Fastly
  Compute's target) — verified by `cargo build --target wasm32-wasip1
  --release` producing a ~1MB `.wasm` binary, well inside Fastly's size
  limit.
- The three building blocks `cmd/ingress-router`'s logic needs all exist on
  Fastly Compute and compose the way `docs/design.md` §16 describes:
  **Dynamic Backends** (proxy to an arbitrary origin resolved at request
  time — here, from a Config Store entry keyed by the token's `tenant_id`),
  a **KV Store** used cache-aside for the AS's JWKS (since a Compute
  instance has no persistent memory between requests — there's no
  equivalent of `go-tokenauth`'s background-refresh goroutine here), and a
  **Config Store** for the `shard_id -> backend URL` map itself.

## What's NOT verified (be honest about this before deploying anywhere)

- **No `fastly` CLI or Fastly account was available to actually build,
  serve, or deploy this** — only `cargo build --target wasm32-wasip1`
  (which uses the same Rust/WASI toolchain `fastly compute build` calls
  under the hood, so it's a real signal, not a rough guess) and `cargo
  clippy` were run. `fastly.toml`'s shape was written from the documented
  schema, not generated by `fastly compute init`, and needs checking
  against a real CLI before it's trusted.
- The AS's own hostname (`AS_HOST` in `main.rs`) is hardcoded rather than
  read from a Config Store entry — a real deployment would want that
  configurable without a rebuild, same as `SHARD_BACKENDS` already is here.
- No integration test exercises the actual Fastly runtime (`fastly compute
  serve` or a deployed environment) — `token-format`'s own tests (in the
  library crate) are what's actually proven against a real token; this
  crate's request-handling logic (`main.rs`) is unverified beyond compiling.
- Dynamic Backends must be enabled for the Fastly service (a one-time
  account-level setting) — `Backend::builder(...).finish()` returns
  `BackendCreationError::Disallowed` if it isn't.

## Building

```sh
# from the rust/ workspace root, or from here directly:
cargo build --target wasm32-wasip1 --release
# -> target/wasm32-wasip1/release/fastly-ingress-sample.wasm
```

This crate is excluded from the workspace's `default-members` (see
`../Cargo.toml`) so a plain `cargo build`/`cargo test` at the workspace
root doesn't need the `wasm32-wasip1` target installed — only building
this crate specifically does (`rustup target add wasm32-wasip1`).

## What a real deployment would still need to configure

- A **Config Store** named `shard_backends`, one entry per shard:
  `default = "https://siros-status-service-ingestion.fly.dev"`.
- A **KV Store** named `jwks_cache` (any Fastly KV Store; the code creates
  its one key, `as_jwks`, lazily on first request).
- **Dynamic Backends** enabled for the service (Fastly support/sales — see
  "What's NOT verified" above).
